* Overview

The Yubikey serves as a hardware security module (HSM)
for protecting the root CA private key. This guide
covers:
- Hardware requirements and selection
- PIV (Personal Identity Verification) setup and
  configuration
- Generating and importing keys
- Using Yubikey with OpenSSL for signing operations
- Security best practices and recovery procedures

The root CA private key **never leaves** the Yubikey;
all signing operations happen on the device itself.

* Yubikey Requirements

** Supported Models

| Model       | PIV | ECDP | Ed25519 | Recommended |
|-------------+-----+------+---------+-------------|
| YubiKey 5   | ✓   | ✓    | ✗       | ✓ RSA/ECDP  |
| Series      |     |      |         |             |
| YubiKey 5   | ✓   | ✓    | ✗       | ✓ FIPS      |
| FIPS Series |     |      |         | if required |
| YubiKey 5C  | ✓   | ✓    | ✗       | ✓ USB-C     |
| YubiKey 5   | ✓   | ✓    | ✗       | ✓ low-      |
| Nano        |     |      |         | profile     |
| YubiKey Bio | ✗   | ✗    | ✗       | ✗ biometric |
| Series      |     |      |         | only        |
| YubiKey NEO | ✓   | ✗    | ✗       | ⚠️ older,    |
|             |     |      |         | limited     |

**Recommendation**: YubiKey 5 Series (standard, USB-A)
or YubiKey 5C (USB-C)
- Firmware version 5.4 or later
- PIV applet enabled (default)
- FIPS version if compliance required

**Note on Ed25519**: YubiKey 5 series does NOT
currently support Ed25519 keys in PIV mode. Use
ECCP384 on the Yubikey for the root, with Ed25519
for intermediate CAs and end-entity certificates.

**Note on RSA-4096**: PIV support for RSA-4096
(and RSA-3072) requires YubiKey firmware **5.7 or
later** — both for on-device generation *and* for
import. On firmware 5.4.x the only available PIV
algorithms are RSA-1024, RSA-2048, ECCP256, and
ECCP384. We recommend **ECCP384** as the root key
algorithm; it is supported on all YubiKey 5.x
firmware and is roughly equivalent to RSA-7680 in
security strength.

**Note on firmware updates**: YubiKey firmware is
*not* user-updatable. Yubico fuses the firmware at
manufacture, so there is no flashing tool, signed
update package, or recovery path — the goal is to
eliminate any code path by which malware (or an
attacker who finds a vulnerability in an update
mechanism) could rewrite the device. To run a
newer firmware version (e.g. 5.7+ for RSA-4096
support), you must buy a new YubiKey. Check the
firmware on a device you already have with
`ykman info`.

** Hardware Considerations

- **Backup strategy**: A YubiKey's key never
  leaves the device, which is fundamentally
  incompatible with conventional backup. See
  [[*Backup & Recovery][Backup & Recovery]] for the three real
  options and the procedure recommended for
  wjmca.
- **Physical security**: Prevent loss or theft
- **Environmental**: Avoid extreme heat/cold;
  keep dry
- **Lifespan**: 5-10 years typical; monitor for
  signs of failure
- **PIN attempts**: Limited (default 3 attempts
  before lockout)

* Initial Yubikey Setup

** Important: Change the default management key

Every YubiKey ships from the factory with three
*publicly documented* default credentials:

| Credential     | Default value                              |
|----------------+--------------------------------------------|
| PIN            | ~123456~                                   |
| PUK            | ~12345678~                                 |
| Management Key | ~010203040506070801020304050607080102030405060708~ |

Anyone with physical access to a YubiKey that
still uses these defaults can generate new keys
in any slot, import certificates, reconfigure the
device, and completely compromise your root CA
infrastructure.

All three must be replaced before the YubiKey
holds any CA material. The steps below do this
in the correct order. If `ykman piv info` ever
shows ~WARNING: Using default Management key!~,
the device is *not* ready for use.

** Step 1: Reset the YubiKey (Clean Slate)

⚠️ WARNING: This deletes everything on the YubiKey.

If the device has been used before (experiments,
another project, a previous CA), reset it now.
For a brand-new factory-fresh device this step
is technically optional, but running it gives a
known starting state.

#+begin_src bash
ykman piv reset
#+end_src

You'll be prompted to confirm. After reset, the
device is back to the factory defaults shown in
the table above.

** Step 2: Replace ALL Default Credentials

⚠️ This is the step that makes the YubiKey safe
to use. Do not skip any of the three commands.
After it, `ykman piv info` must *not* show any
"Using default" warnings.

*** Generate and store a new Management Key

#+begin_src bash
ykman piv access change-management-key --generate
#+end_src

This generates a random 64-hex-character key,
stores it on the YubiKey immediately, and displays
it *once*. Save it before closing the terminal—
if you lose it, the YubiKey must be reset to
recover.

#+begin_src bash
pass insert ca/yubikey-management-key
# Paste the key from the ykman output when prompted
#+end_src

*** Change the PIN

#+begin_src bash
ykman piv access change-pin
#+end_src

- 6–8 digits, unique to this YubiKey
- Example: `847392`
- 3 wrong attempts triggers a lockout (PUK
  required to recover)

#+begin_src bash
pass insert ca/yubikey-pin
#+end_src

*** Change the PUK (PIN unblock key)

#+begin_src bash
ykman piv access change-puk
#+end_src

- 6–8 digits, different from the PIN
- Example: `293847`
- Best practice is to store the PUK in a *separate
  location* from the PIN (see [[*PIN & PUK Management][PIN & PUK Management]]):
  if both leak together, the PUK gives an attacker
  unlimited PIN guesses.

#+begin_src bash
pass insert ca/yubikey-puk
#+end_src

** Step 3: Verify Configuration

#+begin_src bash
ykman piv info
#+end_src

Expected output:

#+begin_src
PIV version: 3.1.2
PIN retries: 3
Management Key Algorithm: TDES
#+end_src

⚠️ If you see *any* of:
- `WARNING: Using default Management key!`
- `WARNING: Using default PIN!`
- `WARNING: Using default PUK!`

go back to [[*Step 2: Replace ALL Default Credentials][Step 2]] and finish replacing the
relevant credential before proceeding.

*** What `certificates export` Does — and Doesn't — Export

A common point of confusion:
~ykman piv certificates export 9c root-ca.pem~
exports the *certificate*, which contains only the
**public key** plus metadata (subject, issuer,
validity, signatures). The **private key never
leaves the Yubikey**.

X.509 certificates are public by design — a TLS
server hands its certificate to every connecting
client. The security of the keypair depends on the
*private* half staying inside the device.

The Yubikey enforces this in hardware:

- On-device-generated private keys cannot be
  extracted. There is no command in `ykman`,
  `yubico-piv-tool`, or OpenSC that exports a
  private key — the chip refuses and there is no
  electrical path off the die for the key
  material.
- `ykman piv keys` has subcommands ~generate~,
  ~import~, ~info~, ~attest~, ~delete~, ~move~ —
  notably **no `export`**.

You can prove it to yourself:

#+begin_src bash
ykman piv certificates export 9c root-ca.pem
openssl x509 -in root-ca.pem -text -noout
# Output shows "Subject Public Key Info:" — a
# public key. There is no "PRIVATE KEY" block.
#+end_src

**The one exception: imported keys.** If you
generated a key with ~openssl genpkey~ and ran
~ykman piv keys import~ (see [[*Option B: Generate Offline, Import to Yubikey][Option B]] and the
multi-Yubikey backup procedure), *you* held the
private key in software before importing it. A
copy may still exist on disk or in backups unless
you securely shredded it. After import, the
Yubikey itself still won't export it — but the
device can't undo the fact that the key once
existed off-device.

**Verifying a key was generated on-device:**
use *attestation*.

#+begin_src bash
ykman piv keys attest 9c attest.pem
openssl x509 -in attest.pem -text -noout
#+end_src

The attestation certificate is signed by a
Yubico-rooted intermediate and proves "this
public key was generated on a real Yubikey, in
this slot, with these touch and PIN policies" —
i.e., the private key has never existed off-
device. Attestation only succeeds for on-device-
generated keys; an imported key cannot be
attested, which is itself a meaningful signal
during an audit.

*** Safety Check Before Generating

**⚠️ WARNING**: Generating a new key in slot 9c
**will overwrite any existing key permanently**.

Before proceeding, ask yourself:

1. **Is slot 9c empty?**
   #+begin_src bash
   yubico-piv-tool -a list | grep "Slot 9c"
   #+end_src
   If it shows nothing, slot 9c is empty and safe to use.

2. **If slot 9c is occupied, do you still have the key?**
   - If YES: You can use the existing key (don't generate
     a new one)
   - If NO: You'll lose access to it if you overwrite

3. **Is this your first time with this Yubikey?**
   - If YES: Run the inspection commands above first

*** Recovering an Existing Key

If slot 9c already has a key and you want to use it:

#+begin_src bash
# Export the certificate
ykman piv certificates export 9c root-ca.pem

# View details
openssl x509 -in root-ca.pem -text -noout

# Use this key for signing (no need to generate new)
# Proceed directly to signing operations
#+end_src

** Option A: Generate Key on Device (Recommended)

The key is generated directly on the Yubikey and
never leaves it:

#+begin_src bash
# Generate ECCP384 key in slot 9c
# (recommended default — supported on all 5.x)
ykman piv keys generate --algorithm ECCP384 \
  --pin-policy once 9c /tmp/root-ca.pub.pem

# When prompted for the Management Key, retrieve
# it from pass:
#   pass show ca/yubikey-management-key
#
# PIN policy 'once' means the user enters the PIN
# once per session.
#
# The trailing positional argument is the path
# where ykman writes the *public* key (recent
# ykman versions require this — older docs that
# omit it will fail with a usage error). The
# private key stays on the device.
#+end_src

Verify the key was created on-device:

#+begin_src bash
ykman piv keys info 9c
# Expected:
#   Algorithm:    ECCP384
#   PIN policy:   ONCE
#   Touch policy: NEVER  (or as configured)
#   Origin:       GENERATED
# "Origin: GENERATED" confirms the key was made
# on the Yubikey (vs. IMPORTED).
#+end_src

*Algorithm alternatives:*

| Algorithm | Firmware | Notes |
|-----------|----------|-------|
| ECCP384 | All 5.x | **Recommended.** Modern ECC, fast |
| ECCP256 | All 5.x | Smaller curve; fine if size matters |
| RSA-2048 | All 5.x | Weaker than ECCP384; widest compat |
| RSA-3072 | 5.7+ | Pure RSA, no firmware-5.4 support |
| RSA-4096 | 5.7+ | Strongest RSA; requires 5.7+ firmware |

The root algorithm does *not* constrain what
intermediate or end-entity certificates can use —
RSA-4096 end-entity certs for legacy devices (e.g.
Grandstream SIP adapters) still work under an
ECCP384 root.

**Slot Assignment** (PIV Standard NIST SP 800-73):

The slot numbers are NOT arbitrary—they're defined
in the official PIV standard used by the U.S.
government for federal ID cards.

| Slot | Official Purpose (NIST) | Our Use |
|------|-------------------------|---------|
| 9a | PIV Authentication | (not used) |
| 9c | Digital Signature | ✓ Root CA signing |
| 9d | Key Management | (not used) |
| 9e | Card Authentication | (not used) |

These slot assignments are standardized across ALL
PIV-compliant devices (Yubikeys, smartcards, etc.).
If you use PIV tools from different vendors, they
all understand these slots the same way.

For our Root CA, we use **slot 9c** (Digital
Signature) because:
- It's the standard slot for signing operations
- OpenSSL and cryptographic tools expect keys here
- All PIV tools recognize 9c as the signing slot

*Why not Ed25519?* YubiKey 5 PIV mode doesn't
support Ed25519 in PIV-compliant slots. Use
ECCP384 for the root (on Yubikey), Ed25519 for
intermediates and end-entity certificates.

** Option B: Generate Offline, Import to Yubikey

If you prefer to generate the key on the CA
machine, then import. The main reason to do this
is the multi-YubiKey backup procedure below, where
the *same* private key must end up on more than
one device.

#+begin_src bash
# Generate ECCP384 key offline
openssl genpkey -algorithm EC \
  -pkeyopt ec_paramgen_curve:P-384 \
  -out /tmp/root-ca.key
chmod 400 /tmp/root-ca.key

# Import to Yubikey (slot 9c)
ykman piv keys import 9c /tmp/root-ca.key

# Securely delete temporary key
shred -vfz -n 3 /tmp/root-ca.key
#+end_src

For RSA-4096 (requires YubiKey firmware 5.7+ on
every device the key is imported into):

#+begin_src bash
openssl genpkey -algorithm RSA \
  -pkeyopt rsa_keygen_bits:4096 \
  -out /tmp/root-ca.key
ykman piv keys import 9c /tmp/root-ca.key
#+end_src

**⚠️ Risk**: Key exists on disk briefly. Only use
this if you must generate offline.

** Step 4: Create Self-Signed Root Certificate

Now create the root CA certificate using the
Yubikey key:

#+begin_src bash
# Generate certificate signing request
# (uses Yubikey key)
ykman piv certificates request 9c root-ca.csr \
  --subject "C=SE,ST=Stockholm,O=Organization,CN=Root CA"

# Self-sign the CSR (using Yubikey to sign itself)
openssl x509 -req -days 7300 -in root-ca.csr \
  -signkey /path/to/key \
  -out root-ca.crt
#+end_src

**Better approach** using OpenSC and PKCS#11:

#+begin_src bash
# Export the public key from Yubikey
ykman piv certificates export 9c root-ca.pub

# Use Yubikey directly for signing (via PKCS#11)
# See "Using Yubikey with OpenSSL" section below
#+end_src

* Using Yubikey with OpenSSL

OpenSSL can interact with Yubikey via PKCS#11
(smart card standard).

** Prerequisites: OpenSC PKCS#11 Module

Verify OpenSC is installed and locate the
PKCS#11 library:

#+begin_src bash
# Linux
find /usr/lib -name "libopensc.so*" 2>/dev/null

# macOS
find /usr/local/lib -name "libopensc*" 2>/dev/null

# Windows
C:\Program Files\OpenSC Project\OpenSC\bin\opensc-pkcs11.dll
#+end_src

** Method 1: Using OpenSC's OpenSSL Plugin

#+begin_src bash
# Set environment variable for PKCS#11 engine
export OPENSC_PKCS11=/usr/lib/x86_64-linux-gnu/libopensc.so

# List available keys/certificates on Yubikey
openssl engine pkcs11 -pre SO_PATH:$OPENSC_PKCS11

# List objects
openssl engine dynamic -pre SO_PATH:/usr/lib/x86_64-linux-gnu/libopensc.so \
  -pre ID:pkcs11 -pre LIST_OBJECTS
#+end_src

** Method 2: Using yubico-piv-tool (Recommended)

The `yubico-piv-tool` makes Yubikey operations
simpler:

#+begin_src bash
# List certificates and keys on device
yubico-piv-tool -a list

# Export public key
yubico-piv-tool -a read-cert -s 9c \
  -o root-ca.pub.pem

# Sign a CSR using Yubikey key
yubico-piv-tool -a sign-csr -s 9c \
  -i intermediate-ca.csr \
  -o intermediate-ca.crt \
  --pin <PIN>
#+end_src

** Method 3: Direct OpenSSL with PKCS#11 (Advanced)

For advanced usage, configure OpenSSL to use
Yubikey directly:

Edit `~/.openssl/openssl.cnf` or create CA-specific
config:

#+begin_src conf
engines = engine_section

[engine_section]
pkcs11 = pkcs11_section

[pkcs11_section]
engine_id = pkcs11
dynamic_path = /usr/lib/x86_64-linux-gnu/engines-1.1/pkcs11.so
MODULE_PATH = /usr/lib/x86_64-linux-gnu/libopensc.so
PIN = 123456
#+end_src

Usage:
#+begin_src bash
# Sign CSR using engine
openssl ca -engine pkcs11 -config openssl.cnf \
  -in intermediate-ca.csr -out intermediate-ca.crt
#+end_src

** Before Each Session

1. Insert Yubikey into USB port
2. Verify it's recognized:
   #+begin_src bash
   ykman list
   #+end_src
3. Authenticate to the device:
   #+begin_src bash

   # Enter PIN when prompted

** Signing Certificates

To sign an intermediate CA CSR with the Yubikey:

#+begin_src bash
# Verify CSR format
openssl req -in intermediate-ca.csr -text \
  -noout -verify

# Use yubico-piv-tool for signing
yubico-piv-tool -a sign-csr -s 9c \
  -i intermediate-ca.csr \
  -o intermediate-ca.crt \
  --pin $(pass show ca/yubikey-pin)

# Verify signed certificate
openssl x509 -in intermediate-ca.crt -text -noout
#+end_src

If PIN is entered incorrectly 3 times, the Yubikey
locks:

#+begin_src bash
# Check PIN retries
ykman piv info

# If locked (0 retries), unblock with PUK
ykman piv access unblock-pin
# Enter PUK when prompted
# Then set new PIN
#+end_src

** Removing Yubikey

When done with a session:

#+begin_src bash

# (Yubikey does not need to be "ejected"

#+end_src

* Security Best Practices

** Physical Security

1. **Possession**: Keep Yubikey on your person
   or in secure location
2. **Backup**: See [[*Backup & Recovery][Backup & Recovery]] for the three
   real options. There is no way to clone an
   on-device-generated key after the fact; you
   must decide the backup model *before* the
   key is created.
3. **Inspect**: Check for signs of tampering
   before each use
4. **Storage**: Use a small case or Faraday bag
   (optional)

** PIN & PUK Management

| Item | Storage | Access | Review |
|------|---------|--------|--------|
| PIN | Password | Root | Monthly |
| | manager | keeper | |
| | (encrypted) | only | |
| PUK | Separate | Root | Yearly |
| | location | keeper | |
| | (safe) | only | |
| Mgmt Key | Password | Root | Monthly |
| | manager | keeper | |
| | | only | |

**Rotation Schedule**:
- PIN: Change annually or when personnel
  changes
- PUK: Change every 2 years
- Management Key: Change every 2 years

** Compromise Procedures

If PIN is compromised:
#+begin_src bash
# Immediately change PIN
ykman piv access change-pin

# Alert team; review signing logs for
# unauthorized activity
#+end_src

If Yubikey is lost/stolen:
1. **Immediately**: Revoke all certificates
   signed by this Yubikey
2. **Report**: Document incident and notify
   stakeholders
3. **Generate new key**: Create new Yubikey
   with new key/cert
4. **Update trust**: Have intermediate CA
   issue new cert from new root

If root CA private key is compromised:
1. **Emergency**: Revoke all issued
   certificates (full CRL)
2. **New root**: Generate completely new root CA
3. **Transition**: Notify all stakeholders;
   announce deprecation date for old root
4. **Infrastructure**: Update clients to trust
   new root CA

* Backup & Recovery

** The Fundamental Tradeoff

A YubiKey's core security promise is that the
private key is generated on the device and never
leaves it. This is *incompatible* with conventional
backup. The moment a backup exists, the key has
existed outside the device.

You must pick one of three approaches *before* you
create the key. There is no fourth option that
gives you both properties—YubiKey PIV does not
support seed-phrase recovery the way some HSMs do.

| Option | Key generation       | Backup?         | Trust anchors | Best for                |
|--------+----------------------+-----------------+---------------+-------------------------|
| A      | Off-device, imported | Yes (clones)    | One           | wjmca (recommended)     |
| B      | On-device, two keys  | No (redundant)  | Two           | Larger PKI teams        |
| C      | On-device, single    | None            | One           | Very small deployments  |

** Option A: Generate Off-Device, Import to Multiple YubiKeys (Recommended for wjmca)

Generate the root key in software on a freshly
booted air-gapped machine, import the *same* key
into 2–3 YubiKeys, then destroy the generating
medium. Every YubiKey then holds the identical
private key and signs the identical root
certificate. Clients see one trust anchor.

*Tradeoff*: the key briefly existed in RAM on a
software machine. The exposure window is the
lifetime of a live USB boot, mitigated by air-gap
and physical destruction of the media afterward.

*** Prerequisites

- 2 or 3 YubiKeys (one primary, one or two backups)
- A live Linux USB (Tails or equivalent)
- A machine with no permanent storage (or with the
  internal drive disconnected) and no network
  access — disable WiFi in BIOS, unplug Ethernet
- A means to physically destroy the USB stick
  afterward (drill, hammer, incinerator, shredder)

*** Procedure

#+begin_src bash
# Step 1: Boot the live USB on the air-gapped
# machine. Confirm no network is active:
ip addr show         # no IPs except loopback
rfkill list          # WiFi/BT should be blocked

# Step 2: Generate the root CA key in tmpfs.
# /dev/shm is RAM-only, never touches disk.
cd /dev/shm
openssl genpkey -algorithm EC \
  -pkeyopt ec_paramgen_curve:P-384 \
  -out root-ca.key
chmod 400 root-ca.key
# (Use RSA 4096 only if every primary AND backup
#  YubiKey is firmware 5.7+: replace the genpkey
#  line with `-algorithm RSA -pkeyopt
#  rsa_keygen_bits:4096`.)

# Step 3: Sanity-check the key
openssl pkey -in root-ca.key -text -noout | head

# Step 4: Insert the PRIMARY YubiKey. Confirm
# it has already had its defaults replaced
# (see "Initial Yubikey Setup" above) — Step 2
# of that procedure must be complete on every
# YubiKey before this point.
ykman piv info

# Step 5: Import the key into the primary
yubico-piv-tool -s 9c -a import-key \
  -i root-ca.key

# Step 6: Generate the self-signed root cert
# (the same cert is used by every YubiKey
# since the key is identical)
openssl req -x509 -new -key root-ca.key \
  -days 7300 -sha256 \
  -out root-ca.crt \
  -config /path/to/root-ca/openssl.cnf

# Step 7: Import the cert into the primary
yubico-piv-tool -s 9c -a import-certificate \
  -i root-ca.crt

# Step 8: Swap YubiKeys; repeat Steps 5 and 7
# for each BACKUP YubiKey. Use the same
# root-ca.key and root-ca.crt.

# Step 9: Securely overwrite the key file
shred -uvz root-ca.key

# Step 10: Power off immediately to clear tmpfs
poweroff
#+end_src

After the machine is off, *physically destroy the
USB stick*. Do not reuse it for anything.

*** Storing the YubiKeys

- *Primary*: With the Root Keeper, in their
  immediate physical custody
- *Backup #1*: In an offline safe (home or office
  vault), sealed in a tamper-evident envelope
- *Backup #2* (optional, recommended): In a bank
  safety deposit box, geographically separated

The Root Keeper should verify the seals on the
backups are intact annually as part of the audit
cycle.

*** Recovery if the Primary YubiKey Fails

#+begin_src bash
# Step 1: Retrieve a backup YubiKey from secure
# storage. Verify the tamper-evident seal was
# intact before opening. If not, treat as a
# compromise — see "Compromise Procedures".

# Step 2: Confirm the backup holds the expected
# key and cert
ykman piv info
ykman piv certificates export 9c - | \
  openssl x509 -text -noout
#+end_src

The PIN, PUK, and management key are *not*
duplicated by the import procedure. Each YubiKey
has its own. Make sure ~pass~ contains the
credentials for the backup device (you set these
during its [[*Step 2: Replace ALL Default Credentials][Step 2]] before importing the key).

Resume normal signing operations using the
backup. The root certificate is identical, so no
clients need re-trust.

Order a replacement YubiKey within a reasonable
window (weeks, not months) to restore the
2-or-3-device pool. You have ~10 years of root
cert validity to do this, but treating the pool
as depleted is not the goal.

** Option B: Dual Independent Roots (Maximum Hardware Security)

Generate a key on YubiKey #1 *on-device* (truly
never leaves). Generate a *different* key on
YubiKey #2, also on-device. Self-sign both as
independent root CAs. Distribute *both* root
certificates to every client's trust store.

If one device fails, the surviving root continues
issuing intermediates. Both keys are
hardware-protected from the moment of generation.

*Tradeoff*: every client must trust two roots; the
certificate chain differs depending on which root
signed the active intermediate. Pinning, HSTS, and
some embedded clients become harder to manage.

Appropriate for larger PKI deployments where the
brief software exposure of Option A is
unacceptable, and where the operational team has
the capacity to manage two trust anchors.

** Option C: Single Device, No Backup (Maximum Purity)

Generate the root key on a single YubiKey,
on-device, never leaves. Accept that loss or
failure of the device requires bootstrapping a
brand new root CA and re-distributing the new
root certificate to every client.

This is more workable than it sounds. The
intermediate CA has a 10-year validity; existing
end-entity certificates remain trustworthy until
they expire. A device loss creates *operational*
work over months, not a security incident.

*Tradeoff*: catastrophic device loss = significant
manual work re-establishing trust at every client.
Not a security failure, but a logistical one that
scales poorly past a handful of clients.

Appropriate for very small deployments where
re-distributing a new root certificate is
manageable, or where the threat model places
"key has never touched software" above all other
concerns.

* Testing & Verification

** Verify Yubikey is Working

#+begin_src bash
# Check device info
ykman piv info

# List all slot contents (algorithm, subject, etc.)
yubico-piv-tool -a status

# Export public key
ykman piv certificates export 9c root-ca.pub.pem

# Verify public key format
openssl x509 -in root-ca.pub.pem -text -noout
#+end_src

** Test Signing Operation

Before using in production, test that signing
works:

#+begin_src bash
# Create a test CSR
openssl req -new -key /tmp/test.key \
  -out /tmp/test.csr \
  -subj "/CN=test.example.org"

# Sign it with Yubikey
yubico-piv-tool -a sign-csr -s 9c \
  -i /tmp/test.csr -o /tmp/test.crt \
  --pin $(pass show ca/yubikey-pin)

# Verify signature
openssl x509 -in /tmp/test.crt -text -noout

# Cleanup
rm /tmp/test.*
#+end_src

** Verify PIN/PUK/Mgmt Key

*** Testing PIN

⚠️ **Note**: `ykman piv info` is read-only and
does NOT require PIN authentication. To actually
test your PIN, use a command that accesses
protected operations:

#+begin_src bash
# Method 1: Test PIN without changing anything
ykman piv access change-pin
# Enter your current PIN when prompted
# Press Ctrl+C when asked for new PIN
# (This confirms the PIN without changing it)

# Method 2: Access protected key information
ykman piv keys info 9c
# Should prompt for PIN

# Method 3: Clear PIN cache, then test
ykman piv access logout
# Now run any protected command:
ykman piv keys info 9c
# Should ask for PIN again
#+end_src

*** Testing PUK

The PUK is only used to unblock a locked PIN. To
test it:

#+begin_src bash
# Check current PIN retries
ykman piv info
# Shows: PIN tries remaining: X/3

# If PIN is locked (0 retries), unblock with PUK
ykman piv access unblock-pin
# Enter PUK when prompted
# Then set new PIN

# To intentionally test PUK (if PIN is not
# locked):
# 1. Enter wrong PIN 3 times
# 2. Run: ykman piv access unblock-pin
# 3. Enter PUK when prompted
#+end_src

*** Testing Management Key

#+begin_src bash
# Test management key without changing it
ykman piv access change-management-key
# Enter current management key when prompted
# Press Ctrl+C when asked for new key
# (This confirms the key without changing it)
#+end_src

* Troubleshooting

** Problem: Yubikey Not Recognized

#+begin_src bash
# Check USB connection
lsusb | grep -i yubico

# Restart smart card daemon
sudo systemctl restart pcscd

# Reinstall drivers (Windows)
# Unplug Yubikey, uninstall in Device
# Manager, reconnect
#+end_src

** Problem: PIN Locked (3 failed attempts)

#+begin_src bash
ykman piv info
# Output shows: PIN retries: 0

# Unblock with PUK
ykman piv access unblock-pin
# Enter PUK when prompted
# Set new PIN
#+end_src

** Problem: "ykman: error: No device to load"

#+begin_src bash
# Check if ykman sees the device
ykman list --serials

# Try resetting USB connection
sudo systemctl restart pcscd

# On Linux, may need to add udev rules
sudo curl https://raw.githubusercontent.com/Yubico/yubikey-manager/master/linux_install/70-u2f.rules | sudo tee /etc/udev/rules.d/70-yubico.rules
sudo udevadm control --reload
#+end_src

** Problem: OpenSSL Can't Access Yubikey

#+begin_src bash
# Verify PKCS#11 module is available
find /usr/lib -name "libopensc.so*"

# Test with pkcs11-tool
pkcs11-tool --module \
  /usr/lib/x86_64-linux-gnu/libopensc.so \
  --list-objects

# Verify engine is installed
openssl engine -t
#+end_src

** Problem: Certificate Verification Fails

#+begin_src bash
# Check certificate details
openssl x509 -in root-ca.crt -text -noout

# Verify signature
openssl x509 -in root-ca.crt -text -noout | \
  grep -A 3 "Subject:"
openssl x509 -in root-ca.crt -text -noout | \
  grep -A 3 "Issuer:"

# If self-signed, Issuer should equal Subject
#+end_src
